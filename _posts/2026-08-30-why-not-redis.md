백테스트 결과 캐시가 pickle 파일 6,048개, 2.7GB까지 늘었다. "이 정도면 Redis나
DB로 옮겨야 하지 않냐"는 질문을 받았고, 옮기지 않기로 판단했다. 크기가 아니라
접근 패턴 때문이다.

---

### 이 캐시가 저장하는 것

백테스트 한 번은 `(종목, 기간, 파라미터 조합)` 하나당 몇 분씩 걸린다. 그런데
청산 규칙만 바꿔서 재실행해도 진입 판정 시뮬레이션은 통째로 같다. 그걸 매번
새로 계산하고 있었다.

그래서 시뮬레이션 결과 자체를 캐싱했다.

```python
def get_or_compute(symbol, start, end, ...):
    key = _cache_key(symbol, start, end, ...)      # sha256 앞 24자
    cache_file = CACHE_DIR / f"{key}.pkl"

    if cache_file.exists():
        with cache_file.open("rb") as f:
            return pickle.load(f)

    result = run_symbol(...)                        # 무거운 부분
    with cache_file.open("wb") as f:
        pickle.dump(result, f)
    return result
```

파일 하나가 평균 460KB다. 안에는 그 조합에서 발생한 주문 객체 전체가 들어 있다.

---

### 접근 패턴이 저장소를 결정한다

이 캐시를 어떻게 쓰는지 보면 답이 나온다.

- **스크립트 실행당 키 하나를 통째로 1회 읽는다.** 부분 조회가 없다.
- **부분 갱신이 없다.** 파라미터가 바뀌면 키 자체가 달라진다.
- **키를 모르는 상태로 검색하지 않는다.** "수익률 상위 10개 조합" 같은 질의를
  이 캐시에 던지지 않는다. 그건 결과를 로드한 뒤 메모리에서 한다.
- **7개 프로세스가 동시에 쓴다.** `ProcessPoolExecutor(max_workers=7)`로 종목별
  병렬 실행하는데, 각 워커가 **자기 키의 파일만** 쓴다.

마지막 항목이 결정적이었다. 파일 기반이면 워커끼리 같은 파일을 건드릴 일이
없어서 **락이 아예 필요 없다.**

---

### 세 선택지를 이 기준으로 비교하면

| | 이 워크로드에서 |
|---|---|
| **파일 blob** | 키로 파일 하나 읽기. 인덱스·쿼리 불필요. 병렬 쓰기 경합 0 |
| SQLite BLOB | 파일 수는 줄지만 pickle이 불투명해 쿼리 이득이 없다. 병렬 쓰기에 락이 생긴다 |
| Redis | 2.7GB를 램에 상주시키고 데몬을 운영해야 한다. 얻는 게 없다 |

Redis를 뺀 이유를 조금 더 쓰면 — Redis는 **작은 값을 초당 수천 번** 읽을 때
쓰는 물건이다. 여기는 460KB짜리를 스크립트 실행당 수십 번 읽는다. 네트워크
왕복과 직렬화가 오히려 붙고, 재시작하면 워밍업이 필요하고, 프로세스가 하나 더
늘어난다. "캐시니까 Redis"는 반사적으로 나오는 답인데 이 조건에는 안 맞는다.

SQLite는 좀 더 아깝다. 파일 6,048개가 한 파일이 되고 원자적 쓰기가 공짜로
따라온다. 그런데 저장하는 게 pickle blob이라 **SQL로 할 수 있는 게 없다.**
`WHERE`도 `JOIN`도 못 쓴다. 그러면 남는 이득은 파일 개수 정리뿐인데, 그 대가로
7개 프로세스의 동시 쓰기 락을 받아들여야 한다.

---

### 같은 프로젝트에서 SQLite를 쓰는 곳도 있다

이게 대비가 돼서 판단이 명확해졌다. 이 프로젝트에는 SQLite 데이터베이스도
있고, 1.6GB다(지금은 2.85GB). 거기 들어가는 건 시세 분봉과 뉴스 원문이다.

그쪽은 접근 패턴이 정반대다.

```sql
SELECT bar_timestamp, close FROM price_bars
WHERE symbol = ? AND bar_timestamp >= ? AND bar_timestamp < ?
ORDER BY bar_timestamp
```

**구간 쿼리가 핵심이다.** "AAPL의 2024년 3월 15일 09:30~10:00" 같은 요청이
계속 들어온다. 이걸 파일로 하면 구간마다 파일을 쪼개야 하고, 경계에 걸치는
요청을 직접 병합해야 한다. 관계형 저장소가 훨씬 낫다.

정리하면 같은 프로젝트에 두 저장소가 있고, 나뉜 기준은 크기가 아니라
**"키로 통째로 꺼내는가, 조건으로 골라내는가"**다.

---

### 남은 문제 하나: 캐시 무효화

파일 기반의 대가도 있다. 파라미터가 바뀌어 키가 달라지면 옛 파일이 그대로
남는데, 이걸 자동으로 정리해주는 게 없다.

실제로 엔진 동작을 바꾸면서 키에 필드 두 개를 추가했더니 기존 6,048개가 전부
무효가 됐다. 지울지 말지 판단이 필요했다.

지우지 않기로 했다. 키가 바뀐 시점에 옛 캐시는 **이미 죽었다** — 어떤 요청도
그 키를 만들지 않으니 잘못 재사용될 경로가 없다. 반면 데이터베이스는 이미 새
데이터로 덮어썼기 때문에, 그 파일들이 **수정 이전 동작을 재현할 수 있는 유일한
기록**이었다. 디스크 2.7GB를 내주고 재현 가능성을 사는 쪽이 낫다고 봤다.

DB였다면 이 선택지가 없었을 수도 있다. 한 파일 안에 섞여 있으면 "옛 것만
남기고 새 것만 쓰기"가 파일 분리만큼 간단하지 않다.

---

### 저장소는 크기가 아니라 접근 패턴으로 고른다

- "2.7GB니까 DB", "캐시니까 Redis"는 크기와 이름만 보고 내리는 판단이다. 실제
  기준은 **어떻게 읽고 쓰는가**다.
- 부분 조회·조건 검색이 없고 키로 통째 꺼내는 워크로드라면, 파일 하나가
  가장 단순하고 병렬 쓰기에도 강하다.
- 반대로 구간 쿼리가 핵심이면 관계형이 맞다. 한 프로젝트 안에서 둘이 공존하는
  게 이상한 게 아니다.
- 대신 파일 기반은 **무효화를 직접 설계해야 한다.** 이번엔 그게 오히려 선택의
  여지를 준 경우였지만, 매번 그렇지는 않을 것이다.
