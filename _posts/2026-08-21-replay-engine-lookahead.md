뉴스 기반 트레이딩 에이전트를 만들면서 가장 먼저 손을 댄 건 전략 로직이 아니라
**백테스트 엔진**이었다. 순서가 뒤바뀐 것처럼 보일 수 있지만, 설계 초기에
백테스트 엔진부터 만든 확실한 이유가 있다.

---

### 룩어헤드(Look-ahead Bias)란 무엇인가

룩어헤드 편향은 백테스트 코드가 **T 시점의 판단을 내릴 때 T 시점 이후의 미래
데이터를 실수로 참조하는 문제**다.

예를 들어 "10:00 시점에 진입 여부를 판단"하는데 코드가 10:05의 가격 데이터까지
이미 볼 수 있는 상태라면, 그 판단은 실전에서 절대 재현 불가능한 '과거 시점의
미래 예측'이 된다. 백테스트 결과만 보면 엄청난 수익률이 나오지만 실거래로
옮기는 순간 계좌가 녹아내리는 전형적인 원인 중 하나다.

이 문제는 크게 두 가지 층위에서 발생한다.

1. **개별 이벤트 판정 시점:** 판단 로직이 미래 가격이나 뉴스를 참조하는 경우
2. **파라미터 튜닝 시점:** 미래 구간 데이터로 고른 파라미터가 과거 평가에
   섞여 들어가는 경우

이 글은 **①번(개별 이벤트 판정 시점의 미래 데이터 참조)을 코드 아키텍처
수준에서 원천 차단한 이야기**다.

---

### 전략보다 엔진을 먼저 만든 이유

프로젝트를 시작하며 세운 2가지 철칙이 있다.

> - 백테스트와 모의거래는 **동일한 전략 코드**를 탄다. (데이터 소스와 브로커
>   어댑터만 교체)
> - 룩어헤드 차단은 **처음부터 설계에 박아넣는다.** 나중에 덧붙이지 않는다.

이 두 원칙은 나중에 지키려고 하면 전략 코드 전체를 재작성해야 할 만큼
리팩터링 여파가 크다. 그래서 전략 로직을 짜기 전에, **전략 코드가 올라갈
뼈대 수준에서 룩어헤드가 구조적으로 불가능한 환경**을 먼저 구축했다.

---

### 벡터화 vs 이벤트 기반: 흔히 빠지는 함정

백테스트 구현 방식은 크게 둘로 나뉜다.

#### 1. 벡터화(Vectorized) 방식

전체 기간 데이터를 Pandas 데이터프레임 등에 다 로드한 뒤, 컬럼 단위로 한
번에 연산하는 방식이다.

```python
df = pd.read_csv("prices.csv")  # 전체 기간 데이터를 메모리에 한 번에 로드
df["signal"] = df["price"].rolling(10).mean()  # 이동평균 계산
```

`rolling(10)`은 기본적으로 과거 10개 행의 평균을 구하므로 문제가 없다.
진짜 위험한 건 `center=True` 같은 옵션을 무심코 쓸 때다.

```python
df["signal"] = df["price"].rolling(10, center=True).mean()  # 🚨 위험: 룩어헤드 발생
```

`center=True`를 주면 현재 행을 기준으로 앞뒤 절반(예: 과거 5개 + 현재 +
미래 4개)을 묶어 평균을 낸다. 즉, 오늘 신호를 만드는 데 아직 오지 않은
미래 4틱의 가격이 섞여 들어간다.

이게 진짜 무서운 이유는 **에러가 안 난다는 점**이다. 코드도 잘 돌고,
차트는 노이즈가 깎여나가 훨씬 매끈해지며, 백테스트 성과는 비정상적으로
좋아진다. 나중에 수익률이 너무 이상해서 코드를 복기할 때가 되어서야
`rolling`, `shift`, `merge_asof` 수십 줄을 되짚으며 버그를 찾아야 한다.

#### 2. 이벤트 기반(Event-driven) 방식

엔진 내부에 '현재 시각(Clock)'이라는 상태를 명시적으로 둔다. `EventFeed`가
이벤트를 시간 순서대로 하나씩 꺼내고, 그때마다 `Clock`이 전진한다.
`Strategy`는 주어진 하나의 이벤트와 제약된 컨텍스트만 받고 판단을 내린다.

```
[Event Feed] ──(시간순 차례대로 1개씩)──> [Clock 전진] ──> [Strategy.judge()]
```

이벤트 기반에서도 백테스트 시점에는 과거 데이터 전체가 파일이나 DB에 다
들어있다. 물리적으로 미래 데이터가 없어서 안전한 게 아니다.

안전한 진짜 이유는 `Strategy`에 전달되는 `Context` 객체에 전체 데이터
조회 메서드나 미래 시점 접근 경로 자체가 아예 없기 때문이다. 영화 파일
전체가 하드디스크에 있어도, 플레이어가 현재 프레임만 출력하고 다음
프레임을 가져오는 버튼을 제공하지 않는 것과 같다.

---

### 3개 컴포넌트로 나눈 구조

엔진의 핵심 규칙: "전략 코드는 '현재 시각까지 공개된 데이터'만 전달받는다.
그 밖의 접근 경로는 존재하지 않는다."

이를 위해 역할과 책임을 3개 컴포넌트로 엄격히 분리했다.

| 컴포넌트 | 역할 | 비고 |
|---|---|---|
| `EventFeed` | 뉴스, 가격 틱, 정정 이벤트를 타임라인 하나로 합쳐 시간순 정렬 | 과거 재생용(Replay)과 실시간 스트림용(Live)이 동일한 인터페이스 사용 |
| `Clock` | "지금 몇 시인가"를 관리하는 단일 진실 공급원(Single Source of Truth) | 시간이 역행하려는 시도가 있으면 즉시 예외(`ValueError`) 발생 |
| `Context` | 전략에 전달되는 유일한 객체 | 주문 제출(`submit_order`), 로그 기록(`log_pass`)만 가능. 조회 메서드 없음 |

```python
class Context:
    """Engine이 생성해서 Strategy에 매 이벤트마다 넘기는 제약된 객체.

    broker는 실행 모드에 따라 주입된다:
    - 백테스트: 가상 체결 시뮬레이터
    - 모의거래: 페이퍼 브로커 API 어댑터
    """

    def submit_order(self, symbol, direction, size) -> OrderResult:
        return self._broker.submit(symbol, direction, size, at=self._clock.now)

    def log_pass(self, event, reason) -> None:
        self._pass_log.append(
            PassRecord(event=event, reason=reason, logged_at=self._clock.now)
        )
```

`Engine`은 이 세 객체를 엮어서 돌리는 단순한 이벤트 루프가 된다.

```python
class Engine:
    def run(self) -> None:
        for event in self._feed:
            self._clock.advance_to(event.timestamp)
            self._dispatch(event)
```

백테스트든 모의거래든 루프는 완전히 동일하며, `EventFeed`와 브로커
어댑터만 교체된다. 전략(`Strategy`)은 자기가 지금 과거 데이터를 돌리는지
실제 시장에 붙어있는지조차 알 수 없고, 알 필요도 없다.

### AI가 제안한 기능을 거절한 이유

`Context`를 설계할 때, Claude가 과거 가격 데이터를 조회하는
`price_history(symbol, lookback="5m")` 메서드를 구조에 슬쩍 포함시켜
두었다. "나중에 판단 보조 피처로 쓸 수도 있지 않겠냐"는 이유였다.

코드를 작성하다가 질문을 던졌다.

> "지금 우리가 검증하려는 핵심 가설에 진짜 가격 데이터가 필요한가?"

현재 확정된 로직은 "뉴스 긍정/부정 판단 → 방향 결정 → 진입"이 전부다.
판단 시점에 가격 데이터를 볼 이유가 없다.

프로젝트 로그에 있던 대안 가설("1차 반응 과잉 후 되돌림 매매")을 염두에
둔 제안이었겠지만, 그건 어디까지나 나중에 검증할 수도 있는 가설일 뿐,
지금 단계의 확정 요구사항이 아니다. 검증도 안 된 가설 때문에 전략
코드가 가격 데이터에 접근할 수 있는 통로를 미리 열어둘 이유가 없었다.

결국 AI의 제안을 거절하고 `price_history`를 `Context` 인터페이스에서
전면 삭제했다. 가격 데이터는 원래 목적대로 오프라인 평가(하네스)용으로만
격리시켰다. YAGNI(You Aren't Gonna Need It) 원칙대로, 나중에 진짜
필요해지면 그때 제약된 인터페이스로 다시 넣으면 된다.

### 검증 및 스모크 테스트

핵심 뼈대를 구성하는 6개 파일(`event_feed.py`, `clock.py`, `context.py`,
`engine.py`, `strategy.py`, `smoke_test.py`)을 작성하고 테스트를 돌렸다.

**기본 순차 처리 검증**: 가짜 뉴스 이벤트 2건을 흘려보냈을 때, 판단
로직을 거쳐 `pass_log`에 정확히 시간순으로 기록되는지 확인했다.

```
OK — 이벤트 2건, 시각순 처리, pass_log 기록 확인됨
```

**시간 역행 차단(Look-ahead) 검증**: `Clock`을 특정 시각으로 전진시킨
뒤, 의도적으로 5분 전 시각으로 돌리는 이벤트를 주입했다.

```
OK: 역행 차단됨 -> ValueError: Clock cannot move backwards
```

의도한 대로 예외를 던지며 엔진이 멈추는 것을 확인했다.

---

판단 시점에 미래 데이터로 접근할 경로 자체를 인터페이스에서 없애면,
전략 코드가 실수로라도 룩어헤드를 일으킬 방법이 없다. "주의해서
안 하기"가 아니라 "접근 자체를 막기"를 택한 이유다.
