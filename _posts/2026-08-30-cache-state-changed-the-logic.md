달라서가 아니라 **직전에 무슨 요청을 했느냐**에 따라서였다.

---

### 조회 구간을 뉴스 시각부터 잡았다

이 전략은 뉴스가 뜬 시점을 기준으로 앞뒤 가격을 본다. 뉴스 **이후** 92분은
포지션을 들고 있을 구간이고, 뉴스 **이전** 30분은 "평소 변동성"을 재는
구간이다.

그런데 가격 데이터를 조회하는 코드는 이렇게 돼 있었다.

```python
TRADE_WINDOW = CONFIRM_DELAY + MAX_HOLD + timedelta(minutes=10)

def _merge_windows(starts, window):
    # 뉴스 시각부터 window 만큼. 겹치면 병합.
    intervals = sorted((s, s + window) for s in starts)
    ...
```

`[뉴스시각, 뉴스시각 + 92분]`. **뉴스 이전 구간이 없다.**

이건 처음 설계할 때는 맞았다. 원래 이 스트림의 용도는 "진입 후 가격을 따라가며
청산 시점을 잡는 것"이었고, 거기엔 과거 데이터가 필요 없었다. 변동성 기준을
나중에 추가하면서 요구사항이 바뀌었는데 조회 구간은 그대로였다.

---

### 대부분의 경우엔 잘 돌아갔다

여기가 이 버그의 고약한 부분이다. 뉴스 이전 데이터가 없는데도 계산이
**성공했다.**

이유는 데이터가 어딘가에서 오고 있었기 때문이다. 뉴스는 몰려서 뜬다. 직전
92분 안에 같은 종목의 다른 뉴스가 있었다면, 그 뉴스가 만든 조회 구간이
지금 필요한 과거 구간을 **이미 채워놨다.**

즉 이렇게 갈렸다.

| | 비율 | 실제 동작 |
|---|---|---|
| 직전 92분에 다른 뉴스 있음 | 34% | 의도대로 |
| 없음 | **66%** | 필요한 봉이 없어서 계산 창이 통째로 한 칸 밀림 |

**같은 코드, 같은 종류의 입력인데 실행 이력에 따라 다른 계산을 하고 있었다.**

---

### 두 집단으로 갈라서 상관계수를 재봤다

처음엔 "대충 비슷하겠지"로 넘어갈 뻔했다. 전체를 뭉뚱그려 재면 상관계수가
0.5쯤 나오는데, 이건 애매한 숫자다. 완전히 무관하지도 않고 일치하지도 않는다.

가설을 세우고 갈라서 봤다. "직전에 뉴스가 있었느냐"로 나누면 두 집단이 서로
다른 계산 방식과 일치해야 한다.

| 표본 | 정렬된 창과 상관 | 한 칸 밀린 창과 상관 |
|---|---|---|
| 직전에 뉴스 있음 (34%) | **0.963** | 0.008 |
| 직전에 뉴스 없음 (66%) | 0.099 | **0.949** |

깔끔하게 갈렸다. 전체를 뭉치면 0.5로 보이던 게, 사실은 **두 개의 다른 동작이
섞여 있던 것**이었다.

**여기서 얻은 방법 하나**: 상관계수가 어중간하게 나오면 "약한 관계"가 아니라
**"서로 다른 두 집단이 섞여 있는 것"**을 먼저 의심해볼 만하다. 가설을 세워
쪼개보면 확인은 금방이다.

### 테스트로 안 잡힌 이유

이 버그는 유닛테스트로 잡히지 않는다. **테스트는 항상 깨끗한 상태에서 돌기
때문**이다.

테스트에서 뉴스 이벤트 하나를 넣으면, 캐시가 비어 있으니 조회 구간이 정확히
`[뉴스, +92분]`만 만들어진다. 그리고 그 조건에서는 코드가 "데이터 없음"으로
정상 처리한다. 버그가 드러나려면 **직전에 다른 요청이 남긴 부수 효과**가
있어야 하는데, 그건 테스트가 일부러 만들지 않는 상황이다.

프로덕션에서만 나타나고 테스트에서는 안 나타나는 차이가 정확히 여기 있었다.

### 고친 방법과 데이터 재수집을 피한 방법

조회 구간을 앞으로 1분 늘렸다.

```python
# [뉴스−1분, +92분] — 뉴스가 14:30:37이면 14:30봉이 포함된다.
# 그 봉의 종가는 14:31에 확정되므로 미래참조는 생기지 않는다.
```

문제는 이걸 바꾸면 **기존 캐시가 전부 미스**가 된다는 점이었다. 구간이
달라지니 캐시 키가 안 맞고, 16만 개가 넘는 구간을 API로 다시 받아야 했다.

여기서 우회로가 있었다. 다른 분석을 하려고 **이미 받아둔 분봉 1,648만 개**가
있었다. 같은 종목, 같은 기간, 같은 원시 1분봉이었다. 이걸 데이터베이스로
옮기면 API 재조회가 필요 없다.

옮기기 전에 확인을 하나 했다. **두 출처가 정말 같은 스케일인가.** 이 프로젝트는
전에 액면분할 조정 여부가 다른 데이터를 섞어서 수익률이 ±90%로 깨진 적이
있었다. 그래서 겹치는 구간 **223,852개 봉을 전수 대조**했고, 불일치 0건을
확인한 뒤에 옮겼다.

결과적으로 API 호출 0회로 데이터베이스가 435만 행에서 1,735만 행이 됐다.

캐시 판정도 같이 고쳤다. 기존에는 `(종목, 시작, 끝)`이 **정확히 일치**해야
히트였는데, 이제 분기 단위 통짜 구간이 저장돼 있으니 그 안의 좁은 구간은
전부 흡수돼야 한다. 판정을 **포함 관계**로 바꿨다.

```sql
-- 전: window_start = ? AND window_end = ?
-- 후: window_start <= ? AND window_end >= ?
```

### 캐시를 읽기 최적화가 아니라 암묵적 상태로 쓰면 재현성이 깨진다

- 캐시는 "있으면 빨리, 없으면 다시 계산"이어야 한다. 이 코드는 **"캐시에 있는
  만큼만 사용"**이었고, 그 순간 캐시가 최적화가 아니라 **로직의 입력**이 됐다.
- 그러면 같은 코드가 실행 이력에 따라 다르게 동작한다. 재현이 안 되고, 테스트가
  못 잡고, 원인을 찾을 때 코드만 봐서는 답이 안 나온다.
- 요구사항이 바뀌었는데 데이터 조회 범위가 그대로면 이런 게 생긴다. 이 경우
  "청산용 스트림"으로 만든 구간을 나중에 "변동성 계산"이 같이 쓰게 되면서
  전제가 깨졌다.
