백테스트 파라미터 하나를 바꾸고 재실행했는데, 결과가 바뀌지 않았다. 에러도
없고 실행 시간도 정상이었다. 캐시가 옛 결과를 그대로 돌려주고 있었다.

---

### 캐시를 넣은 이유

이 프로젝트의 백테스트는 종목·기간 하나당 몇 분씩 걸린다. 그런데 분석
스크립트를 여러 개 돌리다 보면 같은 조합을 반복해서 계산하게 된다. 청산
규칙만 바꿔서 재실행해도 진입 판정 시뮬레이션은 통째로 같은데, 그걸 매번
새로 돌리고 있었다.

그래서 `(종목, 기간, 파라미터)`를 키로 잡고 결과를 pickle로 저장하는 캐시를
만들었다.

```python
def _cache_key(symbol, start, end, multiplier,
               confirm_delay_min, baseline_window_min, peak_retracement_ratio):
    raw = f"{symbol}|{start}|{end}|{multiplier}|{confirm_delay_min}|..."
    return hashlib.sha256(raw.encode()).hexdigest()[:24]
```

함수 시그니처에 있는 파라미터를 전부 키에 넣었다. 그때는 이걸로 충분하다고
생각했다.

---

### 시그니처에 없는데 결과에는 영향을 주는 값

문제는 `MAX_HOLD`였다. 포지션을 최대 몇 분까지 들고 있을지 정하는 값인데,
이건 함수 인자가 아니라 **전략 모듈의 전역 상수**였다.

```python
# core/strategy.py
MAX_HOLD = timedelta(minutes=30)
```

시뮬레이션 함수는 이 값을 인자로 받지 않고 `import`해서 직접 참조한다. 그래서
캐시 키를 만드는 쪽에서는 이 값이 존재한다는 것 자체를 모른다.

이 상태에서 `MAX_HOLD`를 30분에서 90분으로 바꿨다. 그러면 청산 시점이
달라지니 손익이 전부 달라져야 한다. 그런데 캐시 키는 **한 글자도 안 바뀐다.**
그래서 30분 시절에 계산해둔 결과가 조용히 재사용됐다.

에러는 안 난다. 그럴듯한 숫자가 나온다. 그 사이에 검증했던 아이디어 몇 개가
이 오염된 결과 위에서 판정됐다.

---

### 고친 방법: 키를 만들 때 전역 상수를 끌어온다

인자로 안 넘어오는 값을 키에 넣으려면, 키 생성 함수가 그 값을 직접 가져와야
한다.

```python
def _cache_key(symbol, start, end, multiplier, confirm_delay_min,
               baseline_window_min, peak_retracement_ratio):
    # MAX_HOLD는 인자로 안 넘어오고 전역 상수로 참조되는데,
    # 이 값이 바뀌면 결과가 바뀐다. 그래서 굳이 키에 포함시킨다.
    from core.strategy import MAX_HOLD
    max_hold_min = int(MAX_HOLD.total_seconds() // 60)

    raw = f"{symbol}|{start}|{end}|{multiplier}|...|{max_hold_min}"
    return hashlib.sha256(raw.encode()).hexdigest()[:24]
```

키 생성 함수가 전략 모듈을 `import`하는 게 깔끔한 구조는 아니다. 의존 방향도
어색하다. 그래도 이 방식을 택한 이유는, 대안이 "전역 상수를 전부 인자로
승격시키기"인데 그건 호출부 전체를 건드려야 하고, 새 전역 상수가 추가될
때마다 같은 작업을 반복해야 하기 때문이다. 키 쪽에서 흡수하는 게 변경
지점이 적다.

---

### 두 달 뒤에 같은 사고가 반복됐다

이번 주에 엔진의 신호 계산 방식을 두 가지 바꿨다. 변동성을 재는 창의 정의와,
가격 데이터를 조회하는 구간의 시작점이다. 둘 다 진입 신호 자체를 바꾸는
값인데, 처음엔 역시 키에 안 넣었다.

같은 함정이었다. 다만 이번엔 이전 사고를 겪은 뒤라 코드에 주석이 남아 있어서
비교적 빨리 알아챘다.

```python
# 조합과 무관하게 항상 붙인다 — 기본값 자체가 바뀌었으므로
# 그 이전 캐시는 전부 무효가 되는 게 맞다.
raw += f"|bm={baseline_mode}|pw={pre_window_min}"
```

여기서 판단이 하나 갈렸다. 옛 캐시 6,048개를 **지울 것인가**.

지우지 않기로 했다. 키가 바뀐 시점에 옛 캐시는 이미 죽었다 — 어떤 요청도 그
키를 만들어내지 않으므로 재사용될 경로가 없다. 반면 그 파일들은 수정 이전
동작을 재현할 수 있는 **유일한 기록**이다. 데이터베이스는 이미 새 데이터로
덮어썼기 때문에, 파일을 지우면 "수정 전에는 어땠는지"를 다시 계산할 방법이
사라진다. 디스크 2.7GB를 내주고 재현 가능성을 사는 쪽을 택했다.

---

### 캐시 키는 시그니처가 아니라 "결과에 영향을 주는 입력" 기준으로

정리하면 이렇다.

- 캐시 키에 들어가야 하는 건 함수 인자가 아니라 **결과를 바꾸는 모든 값**이다.
  전역 상수, 설정 파일, 환경 변수, 참조하는 다른 모듈의 기본값까지 포함된다.
- 이 종류의 버그는 **조용히 실패한다.** 예외도 안 나고 성능 저하도 없고,
  그럴듯한 숫자가 나온다. 결과가 이상하다고 느껴야만 의심하게 되는데, 그때는
  이미 그 위에서 여러 판단을 내린 뒤다.
- 그래서 "키에 넣을까 말까" 애매하면 넣는 쪽이 낫다. 잘못 넣으면 캐시 미스가
  나서 느려질 뿐이지만, 빠뜨리면 틀린 답이 나온다. 두 실패의 비용이 대칭이
  아니다.
